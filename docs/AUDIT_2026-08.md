---

## 1. The short version

This is a well-engineered project. Not "good for a hobby game" — well-engineered
by the standards you would apply to something you had to maintain with other
people. Three things in particular are better than they need to be:

- **The multiplayer design is genuinely thought through.** Host-authoritative
  with a hand-written snapshot, a poll instead of forty emit sites, and an
  intent authority function that the code itself calls "the whole security
  model of the match" — and then tests. The reasoning for each of those choices
  is written down next to the code that implements it.
- **The test harness tests the game, not a model of the game.** 43 probes, no
  mocks, every one driving the real thing in a real browser. The static gate
  (`qa/parsecheck.sh`) has four checks and every one of them exists because a
  specific bug got past the thing before it.
- **The comments are about *why*.** 21% of the source is comment, and it is not
  narration — it is a record of what was tried, what broke, and what the failure
  taught. Reading this codebase, you learn things.

The problems are correspondingly narrow. Across an arcade sweep of all 22
minigames, both maps booting and playing, Memory Match end to end and two
two-seat online matches, there were **zero uncaught exceptions, zero console
errors and zero orphaned meshes**. What I found instead is one confirmed multiplayer
defect that the design explicitly forbids, one architectural decision that has
quietly closed off unit testing, and a tail of small drift — dead code, silent
sounds, a stale report, an unescaped name.

**The one thing to fix first:** opening the map on the host changes the game
state for everybody. Everything else can wait a build.

## 3. What is good

### 3.1 The networking design

`src/net/` is six small modules with one job each and one module that knows how
they fit. Four decisions in it are worth naming because each one closes off a
whole class of bug rather than fixing an instance:

**A snapshot, not an event log.** The state is touched from about forty places
in the turn flow; the first missed emit in an event-sourced design is a silent
desync that shows up ten minutes later as one phone's token on the wrong square.
A snapshot cannot drift. The cost — bandwidth — I measured at **1.7 KB per
snapshot** on City Circuit. That is nothing.

**A poll, not an emit.** `NetSync` samples the host's own state at 20 Hz and
sends when a cheap signature moves. It cannot be forgotten, and it needs no
imports in the game code. I expected this to be the performance problem in the
build, because `snapshot()` calls `getComputedStyle()` on seven elements every
tick — 140 forced style resolutions a second. **Measured: 0.014–0.034 ms per
tick, about 0.3–0.7 ms of CPU per second.** The hypothesis was wrong; the design
is fine.

**One authority function.** `NetSync.authorised()` is the only thing standing
between a modified client and somebody else's turn, and it is written as such —
including the `ONLY_IN` beat gate, which exists because "the button was not on
screen" guarantees nothing over a wire. The host was later put through the same
function as everybody else, which is the correct instinct.

**A command bus that is a direct call offline.** `Commands.js` imports nothing.
That single constraint is what lets `src/net/` depend on the game without the
game depending on `src/net/`, and it is the cleanest seam in the codebase.

### 3.2 The test harness

43 probes, all driving the real game. The README states the rule outright — "a
probe that passes means the game did the thing" — and then names the two traps
that cost the project real time (`pgrep -f` matching itself; Node block-buffering
a probe's stdout so an empty file reads as "produced nothing" rather than "still
running"). I hit the second one repeatedly during this audit; the warning is
accurate.

`qa/parsecheck.sh` deserves specific credit. Each of its four gates is derived
from a real escape, and the dead-local-reference check is *exact* rather than
heuristic because the codebase committed to a naming convention (`_`-prefixed
file-locals) that makes it exact. That is the right way round: the convention
was chosen so the check could be cheap.

The line **"Looking is a test"** — three layout faults found by screenshotting
at 412×892 and none by any assertion — is the most valuable single paragraph in
the repository.

### 3.3 Structure and discipline

- **No build step, no dependencies, no `package.json`.** ES modules served
  directly, `three` and `cannon` vendored so a blocked CDN cannot blank the
  screen, and a boot guard in `index.html` that renders a real error page with a
  reload button when the engine libraries are missing.
- **Functions are small even though files are large.** GameController is 2,611
  lines but 101 functions — 26 lines average. The outlier is
  `resolveSpaceEffect()` at 206 lines, and it is a flat switch over 21 space
  types, which is the readable shape for that job.
- **Every minigame complies with the standard.** All 22 compute `dt` in seconds
  and cap it at 0.1 s (R1), all 22 register a teardown hook (R3), all 22 take and
  use `botSkill` (§5), and the DOM-only games are the only two without DPR
  handling, which is correct rather than missing.
- **`Director.js` solves scene overlap properly** — a beat owns the screen for a
  floor, `ack()` compresses the remainder for an eager tapper, and `reset()`
  cancels every pending continuation on rematch. This replaced scattered bare
  `setTimeout`s, and nothing can now fire into the next match.
- **`Storage.js` is fully guarded** — every call try/caught, so a private-mode
  browser degrades to "does not remember" rather than "does not run".
- **Settings honours the OS.** On first run, `prefers-reduced-motion: reduce`
  sets the in-game motion preference. Most projects never do this.

### 3.4 The documentation

4,924 lines across 13 documents, and the standard is high enough that I used
them as primary sources rather than checking them. Two habits stand out:

- Every design doc has a **"what has NOT been verified"** section that is
  specific and unflattering. `MULTIPLAYER_PLAN.md` §7 lists four real gaps
  including "how any of this looks on a real phone".
- Failures are written up **with what they taught**, not just what was fixed —
  "a flag with two owners is not a guard"; "an owner beat with no seat has
  nowhere to go". That is institutional memory, and it is why the same bug class
  stops recurring.

## 4. What needs improvement

Severity is impact on a player. Priority is fix order.

### P1 — The one to fix first

#### A-001 · Opening the map on the host changes the game for everyone

**Status:** confirmed by probe · **Files:** `src/ui/UIManager.js:1445`,
`src/net/NetProtocol.js`, `src/net/NetSync.js:129`

`Commands.js` states the rule plainly:

> Deliberately NOT on the bus: opening the map, opening the bounty sheet …
> Putting them on the wire would make one player's map scroll everybody's, which
> is not multiplayer, it is remote control.

The map is indeed off the command bus. But `UIManager.openMap()` writes
`state.gameState = 'MAP'` and `state.cameraState = 'MAP'`, and **both of those
are on the wire** — `gs` and `cam` are the first two fields of every snapshot.

`qa/mapview.js`, two seats over the loopback transport:

```
host with map open : {"gs":"MAP","cam":"MAP","mapUi":"flex","uiLayer":"none"}
every page while the host scouts: ["MAP","MAP"]
authority while the host is scouting: {"gs":"MAP","ap":1,"rollOk":false}
```

Two distinct consequences:

1. **Every other phone's replicated `gameState` and `cameraState` become
   `'MAP'`.** `NetSync._reconcile()` copies any non-`CINEMATIC` camera mode
   across, so the renderer on every other device starts driving toward *that
   device's own* map target. Measured from a still baseline with the host
   otherwise idle: **the client's camera travelled 39 world units**, with the
   only input being the host opening its own map. That is the host moving the
   camera on a phone belonging to somebody who did not ask for it — the exact
   failure the design forbids.
2. **`authorised()` refuses `roll` while the map is open.** `ONLY_IN.roll` is
   `{PRE_ROLL}`; the game state is `MAP`; the active seat's roll intent is
   dropped on the host in silence, with nothing on either screen to say why.
   The probe shows the refusal landing on seat 1 — a *client* whose turn it was —
   while the host held the map.

   **How reachable is that today?** The HUD map button is guarded by
   `isMyTurn()`, so the host cannot reach the map from the board on somebody
   else's turn; the probe called `openMap()` directly. But there are two other
   doors, and one of them is shared: `#btn-junction-map` (your own move only,
   fine) and **`#btn-cb-tour`, "tour the map" on the City Circuit opening
   briefing** — a beat the whole table is looking at, where any device including
   the host can press it. So consequence 1 is live today on every City match
   where the host tours the board; consequence 2 is one unguarded entry point
   away from being a match that stops with no error anywhere.

**The fix is small.** The map is a *view*, not a *beat*: it needs its own local
flag rather than a lease on the shared game state. Either give the map view its
own `state.localView` that is not in the snapshot, or exclude `MAP` from `gs`
and `cam` at the `snapshot()` boundary the way `CINEMATIC` is already excluded
on the way back in.

#### A-002 · A client's map view is unprotected, not safe

**Status:** confirmed by probe (both halves) · **Files:** `src/net/NetSync.js:159`

A client that opens the map keeps it — but only because snapshots are
change-gated. `NetSync` sends nothing while the host's signature is still, so an
idle host leaves the client's local `'MAP'` standing. The probe confirms it holds
for 1.2 s against an idle host, and then confirms what happens when the host
stops being idle:

```
client at open           : {"gs":"MAP",    "cam":"MAP",   "mapUi":"flex","uiLayer":"none"}
client 1.2s later        : {"gs":"MAP",    "cam":"MAP",   "mapUi":"flex","uiLayer":"none"}
client while the host rolls: {"gs":"ROLLING","cam":"FOLLOW","mapUi":"flex","uiLayer":"block"}
```

Read the last row. The map panel is **still on screen** (`mapUi: flex`) but its
game state has been overwritten, its camera has been yanked back to `FOLLOW`, and
the board HUD has been forced back up *underneath it* by `_reconcile()` step 3.
The map's own drag handlers all guard on `state.gameState !== 'MAP'`, so they are
now no-ops. The player is left holding a dead map with a live HUD behind it.

Nothing in `UIManager`'s map code checks `state.netReplica`. On a client the map
works until the game moves — which is worse than not working, because it is a
control that behaves differently depending on what somebody else is doing.

Same fix as A-001. They are one bug wearing two hats.

### P2 — Fix before the next build goes out

#### A-003 · Player names reach `innerHTML` unescaped in eight places

**Status:** confirmed by machine sweep · **Files:** `src/ui/UIManager.js:276,
862, 940, 1237, 1302`, `src/minigames/MinigameManager.js:766, 781` and the
scoreboard headline

`Lobby.js` and `SoloRound.js` — the two most recently written net-facing files —
both define an `_esc()` and use it. Nothing else does. The rival strip, the turn
banner, the bounty tracker and both minigame result screens interpolate
`${p.name}` straight into an `innerHTML` template.

Offline this is inert, because local names come from `PLAYER_SLOTS`. Online it is
not: a peer types their own name, and it arrives at every other device through
the roster and the snapshot.

**Calibrate the severity honestly.** The host clamps a joining name to 14
characters (`NetSession.js`, on both `HELLO` and `NAME`), and 14 characters is
too few for a working `onerror=` payload. So this is not remote code execution
today. What it is: **a length limit doing a job an escape function should be
doing**, in a codebase that already has the escape function written twice. One
`_esc()` promoted to a shared helper and eight call sites closes it permanently,
and stops the 14 from being load-bearing.

#### A-004 · Losing coins is silent; one sound name does not exist

**Status:** confirmed by machine sweep · **Files:** `src/engine/AudioManager.js`,
`src/core/Economy.js`, `src/ui/SoloRound.js`

Cross-referencing the 21 sounds defined against the 20 names used:

- **`sfx('ui_confirm')`** is called in `SoloRound.js` and matches no case in the
  switch. `sfx()` has no `default`, so it does nothing, silently.
- **`coin_loss` and `shop_open` are defined and never played.** `Economy.earnCoins`
  animates and beeps; `Economy.loseCoins` animates and says nothing. A fine, a
  Tollbooth and a Magnet all take coins off you in silence while every gain
  chimes. That asymmetry is a real feel problem, and the sound to fix it is
  already written.

Add a `default: console.warn` to `sfx()`, and add a fifth gate to
`parsecheck.sh` — sound-name parity is exactly the kind of check that file
exists for.

#### A-005 · Only 6 of 22 minigames can be played online

**Status:** read from `MG_NET` · **File:** `src/config/MinigameRegistry.js:142`

`snapstrike`, `oddoneout`, `steadyhand`, `meteordodge`, `lootcatch`, `treeclimb`.
The other 16 are `local` — one phone, two players at opposite ends — and an
online match cycles through the same six.

This is honestly documented (`MULTIPLAYER_PLAN.md` Phase C/D) and it is the right
call to have shipped without it. But it is worth stating in player terms rather
than plan terms: **an online match has 27% of the minigame roster**, and a
six-round City Circuit will show a player four of the same six games. That is the
biggest gap between what the game *is* offline and what it *is* online, and it is
larger than the board-sync work that has had all the attention.

#### A-006 · The board renders at full rate underneath everything

**Status:** measured · **File:** `src/engine/Renderer.js:2290`

`_loop()` has no early return and calls `renderer.render(scene, camera)`
unconditionally. `qa/hostcost.js` raises a full-screen layer over the board and
counts frames on the scene:

```
board frames / 3s, nothing over it : 5
board frames / 3s, fully covered   : 6
the loop stands down when covered  : false
```

(The absolute numbers are meaningless — SwiftShader, three browsers competing.
The *equality* is the finding.)

So during every minigame a phone runs two renderers: a canvas game on top and a
full Three.js scene with district buildings, particles and animated city life
underneath it, plus `Physics.step(dt)` on a dice world nobody is looking at. On a
mid-range Android this is the most likely cause of a minigame that feels sticky,
and it is a four-line fix: skip the body of `_loop()` while `#minigame-layer`
(or the win screen) owns the screen, and on `document.hidden`.

**Not measured on real hardware.** The saving is arithmetically certain; the size
of it is not.

### 4.1 Two things that are decisions, not defects

- **No host migration.** If the host leaves, the match ends. `NetSession.js`
  states this plainly and explains why (transplanting a live turn-flow
  continuation across devices). That is the right scope call, honestly recorded.
- **`user-scalable=no` on the viewport.** An accessibility antipattern in
  general; correct for a game where a stray pinch mid-minigame loses a round.
  Worth revisiting only for the non-game screens (splash, lobby, rules).

## 5. The architectural finding

Everything above is a fix. This one is a direction.

**`src/core/` is not a rules layer.** Six of its thirteen modules import
`src/ui/` or `src/engine/` — four of them the UI directly — and three touch
`document` or `window` themselves:

```
Economy.js       → UIManager, AudioManager
Contracts.js     → UIManager, AudioManager
GameController.js→ UIManager, ModalManager, Renderer, SetPieces, Fx, Physics, Scenes
WinScreen.js     → ModalManager, Scenes, AudioManager, document
Bot.js           → Renderer
Settings.js      → AudioManager, document
```

`Economy.loseCoins()` — which decides whether a Bodyguard charge absorbs a fine —
cannot be called without a DOM, because it animates the coin display on its way
out.

This is the reason there is not a single unit test in a project with 43 test
files. There is nothing to unit-test: every rule needs a browser. So every check
costs a browser launch, a match boot and minutes of wall clock, which is why the
arcade sweep takes eleven minutes and why the loop that catches a regression is
measured in tens of minutes rather than seconds.

The seam is *nearly* there. `Commands.js` imports nothing on purpose and proves
the discipline is understood. `Bot.js` describes itself as deciding "what" while
GameController owns "when and how" — and then imports the Renderer to read a
node's position, which is a geometry query wearing a rendering module's clothes.

**What I would do, in order, and only if a third map is really coming:**

1. Extract board *geometry* (`getNodeT`, `getPos`, `lobeSamples`) out of
   `Renderer.js` into a `src/engine/BoardGeometry.js` with no `THREE` in it.
   `Bot.js` then stops importing the renderer, and the geometry becomes testable
   in Node. This is the cheapest step and it unblocks the next two.
2. Give `Economy` and `Contracts` an event emitter instead of a `UIManager`
   import — they already emit through `Scenes` elsewhere, so the idiom exists.
   Those two files become pure and unit-testable in an afternoon.
3. Leave `GameController` alone. It is the turn-flow continuation machine and
   splitting it is a month of risk for no player-visible gain.

The reason to care is `STAR_TERRITORY_SPEC.md`. `MapRegistry` is a real seam for
map *config*, but there is no seam for map *scene*: every building, prop,
landmark and particle system for both existing maps lives in one 3,888-line
`Renderer.js`, selected by an `if (isHBD)` in `init()`. A third map means a third
block in the same file. `THIRD_MAP_DESIGN.md` argues that "the registry-and-
standard pattern already used for minigames" is what made 22 minigames cheap —
that argument is right, and it applies to scenes exactly as much as it applies to
games. **Build the scene registry before the third map, not after.**

## 6. What I could NOT verify

Stated plainly, because shipping unverified work as done is how the earlier bugs
got out.

- **Anything visual.** SwiftShader software GL in a headless container. Nothing
  here says the board *looks* right.
- **Real-device performance.** The A-006 saving is arithmetic, not a profile. No
  frame-rate measurement on any real handset, and the absolute frame counts in
  this report are worthless as performance numbers.
- **Real WebRTC.** Every networked assertion here is over the loopback
  (`BroadcastChannel`) transport. Signalling, NAT traversal, packet loss and the
  battery cost of a 20 Hz snapshot over a real data channel are all untested by
  me. The author reports one successful two-device run.
- **iOS Safari.** Chromium only. The `100vh` on `#game-container canvas` (three
  uses, no `dvh`/`svh` anywhere) and the fact that `env(safe-area-inset-*)`
  appears exactly once — on `#minigame-layer`, not on the board HUD — both point
  at a notched iPhone as the most likely place for a layout fault. I could not
  test it; I would look there first.
- **Whether any of it is fun.** All 22 minigames execute. The §6 rubric in the
  standard is a human judgement and I did not make it.
- **Balance at three and four seats.** `MULTIPLAYER_PLAN.md` already flags that
  every number in `GameConfig` was tuned for two. I did not re-derive them.
- **Audio.** Muted throughout. The A-004 finding is name parity — that the
  sounds are *wired*, not that they sound good.
- **Reduce-motion's actual reach.** `body.reduce-motion` has four CSS rules and
  kills CSS animation. Nothing suppresses the *3D* motion — the opening flyover,
  the swap cinematic, the camera follow — which is where motion sickness
  actually comes from. I read this; I did not test it with a person.

## 7. If I could only do five things

1. **Take `MAP` off the wire** (A-001/A-002). One flag, and the design goes back
   to matching its own stated rule.
2. **Stand the render loop down under a full-screen layer** (A-006). Four lines,
   and it is the most likely single win for how the game *feels* on a mid-range
   phone.
3. **One `_esc()`, eight call sites** (A-003), and stop a 14-character clamp from
   being a security control.
4. **Write the root `README.md`** (A-017) and date-stamp the old QA report
   (A-016). The project's documentation is its best asset and the front door is
   missing.
5. **Extract board geometry from the renderer** (§5, step 1) *before* Star
   Territory starts. It is the cheapest of the three structural steps and it is
   the one that gets the first unit test into the repository.
